# ClassMesh Windows Media Probe

`classmesh-media-probe.exe` is the first hardware validation tool for the teacher-presentation hot path:

```text
Desktop Duplication BGRA texture
        ↓ GPU only
D3D11 Video Processor
        ↓
NV12 surface from a bounded pool
        ↓
Media Foundation hardware H.264 encoder
        ↓
encoded H.264 access units
```

The probe is intentionally separate from the normal Service-driven Worker. A driver or hardware-encoder problem therefore cannot affect the classroom service while the media path is still being qualified.

## Getting the diagnostics

The Windows CI job builds release binaries and uploads two artifacts:

```text
classmesh-media-probe-windows-x64
classmesh-media-receiver-windows-x64
```

The executables are:

```text
classmesh-media-probe.exe
classmesh-media-receiver.exe
```

Run the probe from the signed-in interactive Windows desktop that will act as the teacher machine. Do not run this first hardware test from Session 0 or as a Windows service.

## First validation run

Open PowerShell in the directory containing the executable and run:

```powershell
.\classmesh-media-probe.exe --seconds 15 --output .\classmesh-probe.h264
```

The output file is optional. To test only capture/conversion/encoding and print metrics:

```powershell
.\classmesh-media-probe.exe --seconds 15
```

During the run, play a moving 1080p video or move windows continuously so the capture path is not measuring a mostly static desktop.

## Expected teacher-side console output

A successful run should report:

- the selected DXGI display and adapter identity;
- the selected Media Foundation hardware H.264 encoder;
- source texture geometry and the bounded presentation geometry;
- periodic counts for captured, submitted and encoded frames;
- keyframe count;
- rate-drop count when capture is faster than the 30 fps presentation target;
- pool-drop count;
- number of NV12 surfaces currently in flight;
- total encoded bytes.

The first performance gate is not a fixed benchmark score. It is:

1. no CPU bitmap/readback path;
2. encoded frames continue to advance for the entire run;
3. the bounded NV12 pool does not grow;
4. no permanent DXGI fallback is introduced;
5. no process disconnect or unbounded latency queue appears.

A healthy 60 Hz desktop may show `rate_drop` increasing because the presentation encoder is deliberately paced at 30 fps. That is expected and preferable to queueing old frames.

`pool_drop` should normally remain low or zero. A steadily increasing `pool_drop` means the encoder is not returning surfaces quickly enough and requires investigation before classroom fan-out work continues.

## Two-machine end-to-end UDP test

After the local hardware probe succeeds, ClassMesh can exercise the real teacher-to-student encoded media path.

On the student/test machine, allow the chosen UDP port through the local firewall. To validate only transport/reassembly and save the encoded stream:

```powershell
.\classmesh-media-receiver.exe --listen 0.0.0.0:57000 --seconds 30 --output .\received.h264
```

To extend the same test through the student GPU decoder without displaying a window, add `--decode`:

```powershell
.\classmesh-media-receiver.exe --listen 0.0.0.0:57000 --seconds 30 --decode
```

To run the current end-to-end diagnostic through decode **and GPU presentation**, use `--render`:

```powershell
.\classmesh-media-receiver.exe --listen 0.0.0.0:57000 --seconds 30 --render
```

`--render` implies hardware decode and opens the current 1280×720 diagnostic window titled `ClassMesh Student Presentation`. A raw H.264 copy may still be collected independently:

```powershell
.\classmesh-media-receiver.exe --listen 0.0.0.0:57000 --seconds 30 --render --output .\received.h264
```

On the teacher machine, replace `STUDENT_IP` with the student machine's LAN IPv4 address:

```powershell
.\classmesh-media-probe.exe --seconds 30 --udp-to STUDENT_IP:57000
```

The teacher continues to capture, convert and hardware-encode exactly once. Each completed `SharedEncodedFrame` is packetized into bounded ClassMesh UDP media datagrams and sent immediately; the sender does not build a reliable video queue.

The receiver prints:

- datagrams received;
- completed/reassembled frames;
- encoded bytes;
- keyframes;
- observed sequence gaps;
- reordered/duplicate datagrams;
- NACK requests generated by the bounded receiver window;
- stale-frame drops and keyframe-recovery requests;
- decoded GPU-frame count when `--decode` or `--render` is enabled;
- presented-frame count when `--render` is enabled;
- presentation errors separately from decode errors;
- frames skipped while waiting for a recovery keyframe.

With `--decode` or `--render`, ClassMesh creates a hardware D3D11 video device, starts Media Foundation, enumerates H.264 decoder candidates, and accepts only a decoder that can expose D3D11-backed NV12 output. It does not silently fall back to WARP or a CPU pixel path. After loss or a decoder error, the diagnostic flushes the decoder and waits for a new keyframe before resuming.

With `--render`, the presentation path is:

```text
ClassMesh UDP reassembly
        ↓
Media Foundation H.264 hardware decoder
        ↓
IMFDXGIBuffer / ID3D11Texture2D (NV12)
        ↓ GPU only
D3D11 Video Processor
        ↓
BGRA flip-discard swap-chain backbuffer
        ↓
ClassMesh Student Presentation window
```

There is no staging readback, `Bitmap`, JPEG conversion, or CPU pixel conversion in this presentation path. Source aspect ratio is preserved with letterboxing or pillarboxing where necessary.

Decode and presentation remain separate health domains. A D3D11 presentation failure increments `present_errors`; it does not by itself mark the decoder, network receiver, device, or control session offline. Closing the diagnostic presentation window stops the standalone receiver cleanly.

`received.h264` remains optional and exists only as an independent diagnostic sink. Hardware decode/render does not require writing the stream to disk.

NACK/keyframe feedback is modeled in the network layer but this standalone diagnostic still does not send feedback back to the teacher over the reliable control channel. Missing media therefore remains visible in the counters instead of being hidden by a TCP/JPEG fallback.

### Current renderer limitations

The current presentation window intentionally validates the first GPU-native end-to-end path before UI integration. Its output size is fixed at creation time. Full `WM_SIZE`/`ResizeBuffers` handling, swap-chain recreation, and renderer recovery after `DXGI_ERROR_DEVICE_REMOVED` / `DXGI_ERROR_DEVICE_RESET` are the next hardening stage. Do not interpret a successful CI build as physical-GPU runtime qualification; the two-machine hardware test is still required.

## Resolution behavior

The teacher probe never upscales and caps the initial presentation rendition at 1920×1080 while preserving aspect ratio and forcing even NV12 dimensions. Examples:

| Capture texture | Presentation target |
| --- | --- |
| 2560×1440 | 1920×1080 |
| 1920×1200 | 1728×1080 |
| 1366×768 | 1366×768 |

The source dimensions come from the actual Desktop Duplication texture rather than only from desktop coordinates so rotated-display resource geometry can be handled correctly.

## What to collect if the probe fails

Save the complete console output and collect the GPU/driver identity with:

```powershell
Get-CimInstance Win32_VideoController |
    Select-Object Name, DriverVersion, AdapterCompatibility, VideoProcessor
```

Also note:

- Windows version/build;
- whether the machine has Intel, NVIDIA, AMD, or hybrid graphics;
- monitor resolution and refresh rate;
- whether HDR is enabled;
- whether the failure occurred in capture, encode, transport, decode, or presentation;
- whether frames had already rendered successfully before the failure.

Do not work around an encoder/capture/decoder/renderer failure by silently switching the teacher presentation path to JPEG over TCP. The failure should remain observable so ClassMesh can select or repair a real-time video path deliberately.

## Follow-up validation

After the 15-second local encode run is stable, repeat with:

```powershell
.\classmesh-media-probe.exe --seconds 300
```

Then repeat the two-machine UDP + `--render` test for several minutes while playing continuous motion. The five-minute run is the next soak gate before the presentation pipeline is enabled inside the normal Worker lifecycle.

Later qualification expands to Intel Quick Sync, NVIDIA, AMD, multi-monitor, rotation, HDR, window resizing, lock/unlock, sleep/resume, GPU reset/device removal and display-topology changes.
